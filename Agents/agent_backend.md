Arquitetura em Camadas Estrutura obrigatória: **Model → Repository → Service → Controller**. ``` src/main/java/com/barbearia100erro/ ├── model/          # Entidades JPA ├── repository/     # Interfaces Spring Data JPA ├── service/        # Regras de negócio e validações ├── controller/     # Endpoints REST (apenas orquestram a chamada) ├── dto/            ├── security/       ├── exception/      ├── constants/      └── config/         ``` # Objetos de entrada e saída (request/response) # Configuração de segurança, filtro/token, hash # Exceções de negócio e GlobalExceptionHandler # Constantes de papéis e status (String) # Configurações gerais (CORS, seed inicial, propriedades) ### Responsabilidades - **Model:** apenas mapeamento e estrutura de dados. Sem regra de negócio. - **Repository:** acesso a dados e consultas. Sem regra de negócio. - **Service:** **toda** regra de negócio, validação de valores permitidos (status, papel, método), transações (`@Transactional`) e verificação de propriedade dos dados. - **Controller:** recebe a requisição, valida o DTO, chama o Service e devolve a resposta HTTP. **Nunca** contém regra de negócio nem acessa Repository diretamente. --- ## 4. Convenções Obrigatórias ### 4.1 Sem Enums - **Não use `enum` no Java.** Status, papéis e métodos são campos `String`. - Centralize os valores permitidos em **classes de constantes** (`public static final String`) no pacote `constants`, e valide no **Service**. ```java public final class Papeis { public static final String CLIENTE = "CLIENTE"; public static final String ADMIN = "ADMIN"; private Papeis() {} } ``` Constantes esperadas: `Papeis`, `StatusAgendamento`, `StatusPagamento`, `MetodosPagamento`. ### 4.2 Entidades e DTOs - **Nunca exponha entidades JPA nas respostas da API.** Use DTOs de request e response. - **O campo `senha` jamais aparece em nenhuma resposta.** - Use `@Getter`, `@Setter`, `@NoArgsConstructor`, `@AllArgsConstructor` e `@Builder` do Lombok. **Evite `@Data` em entidades** com relacionamentos (risco de loops em `equals`/`hashCode`/`toString`). - Relacionamentos `@ManyToOne` e `@OneToOne` com `fetch = FetchType.LAZY`, evitando o problema N+1. - IDs do tipo **`Long`**, com `@Id` e `@GeneratedValue(strategy = GenerationType.IDENTITY)`. Nas rotas, `{id}` e parâmetros como `servicoId` são numéricos (`Long`). - Datas com `LocalDate` e `LocalDateTime`. `criadoEm` e `atualizadoEm` preenchidos automaticamente (`@PrePersist`/`@PreUpdate` ou `@CreationTimestamp`/`@UpdateTimestamp`). ### 4.3 Nomes e banco - Classes em português, no singular: `Usuario`, `Servico`, `Agendamento`, `Pagamento`, `Promocao`. - Tabelas no plural, via `@Table(name = "...")`: `usuarios`, `servicos`, `agendamentos`, `pagamentos`, `promocoes`. - Evite nomes de colunas que sejam palavras reservadas do H2 (ex.: `user`, `value`). - Mantenha o mapeamento **agnóstico de banco** (sem SQL nativo específico do H2), para permitir migração futura. --- ## 5. Regras de Negócio por Service ### 6.1 `UsuarioService` - Cadastro público cria **sempre** `papel = "CLIENTE"`. O campo `papel` **nunca** é aceito vindo do cliente no cadastro. - `email` único (tratar duplicidade com erro `409 Conflict` claro). - Senha salva **somente com hash**. - Cliente só lê e edita **o próprio** perfil. - Admin pode listar clientes e consultar o **histórico** de cada um (frequência, serviços, valores). - A conta `ADMIN` **não é criada por endpoint público** (ver seção 8.3). ### 6.2 `ServicoService` - Catálogo público lista apenas serviços com `ativo = true`. - Apenas `ADMIN` cria, edita e ativa/desativa serviços. - Preferir **desativar** (`ativo = false`) em vez de excluir serviços já usados em agendamentos, para preservar o histórico. ### 6.3 `AgendamentoService` - Apenas usuário **autenticado com papel `CLIENTE`** cria agendamento (o cliente vem do usuário logado, não do corpo da requisição). - O serviço escolhido deve estar **ativo**. - `dataHoraFim = dataHoraInicio + serviço.duracaoMinutos`. - **Não permitir agendar no passado.** - Horário dentro do **expediente configurado** (ver seção 9). - **Verificação de conflito** (agenda única): um novo agendamento é inválido se existir outro, com status `PENDENTE` ou `CONFIRMADO`, em que `inicioExistente < novoFim` **e** `fimExistente > novoInicio`. Retornar `409 Conflict`. - A verificação de conflito e a gravação devem ocorrer **na mesma transação**, para evitar dois clientes reservando o mesmo horário. - Status inicial: `PENDENTE`. - **Transições de status permitidas:** - `PENDENTE` → `CONFIRMADO` (automático após pagamento `PAGO`) - `CONFIRMADO` → `CONCLUIDO` (ação do admin) - `PENDENTE` ou `CONFIRMADO` → `CANCELADO` (cliente, respeitando a política de cancelamento, ou admin) - Qualquer outra transição deve ser rejeitada (`400` ou `409`). - Cliente só vê, cancela e paga **os próprios** agendamentos (`403`/`404` caso contrário). - Endpoint de **disponibilidade**: dado um serviço e uma data, retorna os horários livres, calculados a partir do expediente, da duração do serviço e dos agendamentos existentes. - *(Opcional, alinhar com o Master)* Agendamentos `PENDENTE` sem pagamento após X minutos são cancelados automaticamente para liberar o horário. ### 6.4 `PagamentoService` — pagamento simulado - **Não existe gateway real, nem cobrança, nem integração externa.** Todo o fluxo é simulado. - Fluxo: o cliente envia o método de pagamento → o Service valida o agendamento (do próprio cliente, em status `PENDENTE`, sem pagamento prévio) → simula o resultado → grava o `Pagamento`. - Simulação: gerar `transacaoGatewayId` fictício (`"SIM-" + UUID`) e definir `statusPagamento`: - `"PAGO"` no cenário padrão (preencher `pagoEm`). - `"FALHOU"` em cenário de recusa simulada (a regra de quando ocorre — por exemplo, um valor/método de teste — deve ser definida com o Master). - Se `PAGO`: o agendamento passa para `CONFIRMADO`. Se `FALHOU`: permanece `PENDENTE`, e o cliente pode tentar novamente. - `DINHEIRO_PRESENCIAL`: manter o pagamento como `PENDENTE` até o admin confirmar o recebimento, ou tratar conforme regra definida pelo Master. - **Isole a simulação** atrás de uma interface (ex.: `GatewayPagamento` com implementação `GatewayPagamentoSimulado`), de modo que um gateway real possa substituí-la no futuro sem alterar o restante do sistema. - `valor` do pagamento vem do **preço do serviço no servidor**. Nunca confie em valor enviado pelo cliente. ### 6.5 `PromocaoService` - Público vê apenas promoções com `ativo = true` e **vigentes** (`dataInicio ≤ hoje ≤ dataFim`). - Apenas `ADMIN` cria, edita e desativa. - *(Definir com o Master)* Se o desconto da promoção é aplicado automaticamente ao `valor` do pagamento; se for, a regra de qual promoção prevalece quando houver mais de uma vigente. ### 6.6 Relatórios e dashboard (`RelatorioService`) - O **faturamento** considera apenas agendamentos `CONCLUIDO` com pagamento `PAGO`. - Métricas mínimas para o admin: faturamento do mês, quantidade de atendimentos, ticket médio, serviços mais vendidos e taxa de ocupação da agenda. - Também: clientes aniversariantes do mês (apoio à fidelização). --- ## 7. Autenticação e Autorização ### 8.1 Princípios - **Quem não está logado só acessa o público** (catálogo e promoções). - Cliente precisa de **cadastro e login** para agendar. - Admin tem **login próprio** e acessa a área administrativa pela rota `/admin` no Front-End. - **A autorização é validada no Back-End.** Todas as rotas `/api/admin/**` exigem papel `ADMIN`; esconder telas no Front-End **não** é segurança. - Resposta correta: `401` (não autenticado) e `403` (autenticado sem permissão). - Cliente acessa **apenas os próprios dados**. ### 8.2 Recomendação de implementação - **Spring Security** com senha em **BCrypt**. - Para um Front-End em SPA, preferir **JWT stateless** (com expiração) enviado no header `Authorization: Bearer`. Confirmar a escolha com o Master (sessão × JWT). - Configurar **CORS** liberando apenas a origem do Front-End. - Nunca registrar senhas ou tokens em log. ### 8.3 Conta de administrador - Criada por **seed na inicialização** (ex.: `CommandLineRunner`), **somente se ainda não existir**. - E-mail e senha iniciais vêm de **propriedades/variáveis de ambiente**, nunca fixos em código nem versionados no repositório. - Não existe endpoint público que crie `ADMIN`. --- ## 9. Configuração (H2 e propriedades) ### 9.1 H2 - Usar **modo arquivo**, para que agendamentos e histórico **sobrevivam ao reinício** da aplicação (o modo em memória apaga tudo ao reiniciar e só serve para testes). - `ddl-auto=update` é aceitável durante o desenvolvimento. Tratamento de Erros - Use um `@RestControllerAdvice` (`GlobalExceptionHandler`) com exceções de negócio próprias. - Formato padronizado de erro, para o Front-End exibir mensagens amigáveis: ```json { "timestamp": "2026-10-22T14:30:00", "status": 409, "erro": "Conflito", "mensagem": "O horário escolhido não está mais disponível.", "caminho": "/api/agendamentos" } ``` | Situação | Código HTTP | |---|---| | Dados inválidos / valor de status fora do permitido | 400 | | Não autenticado | 401 | | Sem permissão | 403 | | Recurso não encontrado | 404 | | Conflito (e-mail duplicado, horário ocupado, transição inválida) | 409 | - Mensagens em **português** e sem expor detalhes internos (stack trace, SQL). --- ## 11.
